# Правила работы с проектом

Этот файл действует на весь репозиторий. Он закрепляет существующую архитектуру проекта и не
является поводом для массового рефакторинга соседнего кода. Перед изменением изучи ближайшие
аналоги и сохраняй принятый в модуле стиль.

## Контекст проекта

-   SPA на React 18 и TypeScript со сборкой Webpack 5.
-   Маршрутизация: React Router 6.
-   Серверное состояние: TanStack Query.
-   Общее клиентское состояние: Zustand.
-   Формы: React Hook Form и Yup.
-   Стили: Emotion и дизайн-токены в CSS custom properties.
-   Поддерживаемая среда: Node.js `>=16.14.0`, npm `>=8`.

## Структура папок

-   `src/pages` — route-level страницы. Здесь собираются пользовательские сценарии из features,
    widgets и общих компонентов; переиспользуемую предметную логику сюда не помещай.
-   `src/features` — предметные модули и переиспользуемая бизнес-логика конкретной области.
-   `src/components` — общие компоненты. Соблюдай существующие категории `ui`, `form`, `core`,
    `interaction`, `containers` и `other`.
-   `src/widgets` — крупные составные блоки интерфейса, объединяющие несколько компонентов или
    features.
-   `src/api/<domain>` — низкоуровневые HTTP-функции и типы контрактов конкретного ресурса.
-   `src/api/queries/<domain>` — TanStack Query hooks поверх функций из `src/api`.
-   `src/router` — константы путей, конфигурация маршрутов и route helpers.
-   `src/hooks`, `src/utils`, `src/types`, `src/styles` — только действительно общая
    инфраструктура. Доменно-специфичный код оставляй внутри соответствующего feature или page.
-   Store, hook или helper, нужный только одному модулю, размещай рядом с этим модулем. Поднимай
    его в общий слой только после появления реального переиспользования.

Не создавай новый верхнеуровневый слой без необходимости и не перемещай существующий код между
слоями в рамках несвязанной задачи.

## Разбиение модулей по файлам

Для страниц и компонентов используй существующую структуру каталога:

-   `index.tsx` — React-компонент и его композиция;
-   `units.ts` — Emotion styled-компоненты;
-   `types.ts` — публичные props, интерфейсы и сложные локальные типы;
-   `const.ts` — константы и статические отображения;
-   `utils.ts` или `utils.tsx` — чистые вспомогательные функции;
-   `form.ts` — тип значений формы и Yup-схема;
-   `store/index.ts` и `store/types.ts` — Zustand store и его контракт;
-   `components/` — части, имеющие самостоятельную ответственность внутри владельца;
-   `index.ts` — публичный barrel export каталога.

Не создавай отдельный файл ради одного тривиального типа или константы. Извлекай код, когда у
него появилась отдельная ответственность, повторное использование или когда это заметно
упрощает основной компонент. Сначала размещай вложенный компонент рядом с владельцем, а не в
глобальном `src/components`.

## Работа с API

-   Не выполняй `fetch`, `axios` или вызовы Axios wrapper прямо в UI-компонентах. Компоненты должны
    работать с query/mutation hooks.
-   Низкоуровневый запрос размещай в `src/api/<domain>/index.ts`, а DTO и типы ответа — в соседнем
    `types.ts`.
-   Используй общий `utils/api/axiosWrapper`; не создавай отдельный Axios instance и не обходи его
    auth interceptors.
-   Базовый адрес сервиса бери из `src/api/const.ts`. Не встраивай host или gateway prefix в
    компонент.
-   Для чтения данных создавай `useQuery`, для изменений — `useMutation` в
    `src/api/queries/<domain>`. Не дублируй серверные данные в Zustand.
-   Query key должен начинаться со стабильной константы домена и включать все параметры, влияющие
    на результат. Для запросов с необязательными параметрами явно задавай `enabled`.
-   Преобразование API-ответа в удобную для UI модель выполняй в query layer или чистом mapper, а
    не во время рендера в нескольких компонентах.
-   После успешной мутации инвалидируй связанные query keys через `queryClient`. Не очищай весь
    кэш без необходимости.
-   Не подавляй ошибки пустым `catch`. Ошибка должна остаться доступна TanStack Query либо быть
    показана пользователю через ошибку формы или `Snackbar`.

## Стайлинг

-   Используй `@emotion/styled`. Styled-компоненты храни в соседнем `units.ts` и импортируй в
    компонент как `import * as S from './units'`.
-   Сначала переиспользуй компоненты из `src/components/ui`, `form`, `containers` и других общих
    каталогов; не дублируй их стили на уровне страницы.
-   Для цветов, фонов, границ и типографики предпочитай дизайн-токены вида `var(--...)` из
    `src/styles/design-tokens`. Жёстко заданный цвет допустим только при отсутствии подходящего
    токена и должен быть обоснован контекстом задачи.
-   Динамические style props типизируй. Не передавай в DOM служебные props, если Emotion не должен
    их пробрасывать.
-   Глобальные правила добавляй только в `src/styles`, если они действительно нужны всему
    приложению. Не используй inline styles для постоянной разметки.
-   Не редактируй сгенерированные дизайн-токены в рамках несвязанной задачи.

## Роутинг

-   Все переиспользуемые сегменты путей объявляй в `src/router/const.ts`; не размножай строковые
    литералы маршрутов по приложению.
-   Новую страницу экспортируй через соответствующий barrel в `src/pages` и регистрируй в
    центральном `src/router/index.tsx`.
-   Для переходов и параметров используй API React Router 6: `useNavigate`, `useParams`,
    `useSearchParams` и `createSearchParams`.
-   Маршруты администратора защищай существующим `withAdminRole`, сохраняя поведение загрузки
    ролей.
-   При добавлении полноэкранной страницы проверь `PATHS_WITHOUT_HEADER` и
    `PATHS_WITHOUT_FEEDBACK`. Изменяй эти списки только если макет страницы действительно этого
    требует.
-   Составляй путь из констант роутера. Query-параметры не включай в path constants.

## State management

Выбирай минимально необходимый уровень состояния:

1. `useState`/`useReducer` — локальное состояние компонента или страницы.
2. React Hook Form — значения и ошибки формы.
3. TanStack Query — данные, полученные от сервера, статусы загрузки и мутации.
4. Zustand — разделяемое клиентское состояние, которое нужно несвязанным компонентам.

-   Не копируй query data в Zustand и не создавай глобальный store ради состояния одной страницы.
-   Типы store держи рядом в `store/types.ts`; называй hook в формате `use...Store`.
-   Читай только нужные поля через selector, чтобы не вызывать лишние рендеры.
-   `persist` применяй только когда состояние должно переживать перезагрузку. По возможности
    ограничивай сохраняемые поля через `partialize` и не сохраняй токены, секреты или временные
    статусы.
-   Обновления store должны быть явными actions. Сохраняй существующий `defaultValues`/reset
    pattern, если store поддерживает очистку.

## Формы

-   Используй React Hook Form. Корневую форму создавай через `useForm`, передавай контекст через
    `FormProvider`, а поля бери из `src/components/form`.
-   Тип `FormValues` и Yup-схему размещай в соседнем `form.ts`. Для динамической схемы используй
    функцию `getValidationSchema(...)`.
-   Подключай Yup через `yupResolver`; пользовательские тексты ошибок должны быть понятными и
    соответствовать языку интерфейса.
-   Вложенные поля получают форму через `useFormContext`, повторяющиеся наборы — через
    `useFieldArray`. Не передавай весь form object через несколько уровней props.
-   Для данных, загруженных асинхронно, вызывай `reset` в effect с полным набором ожидаемых
    значений. Указывай безопасные default values для массивов, строк и nullable полей.
-   До вызова мутации явно преобразуй `FormValues` в API DTO. Не связывай форму напрямую с
    несовпадающим серверным контрактом.
-   Ошибки конкретного поля устанавливай через `setError`; общий успешный или ошибочный результат
    сообщай через существующий `Snackbar`. Блокируй повторную отправку во время мутации, если это
    необходимо для сценария.

## TypeScript и кодстайл

-   Проект работает в strict-режиме. Добавляй точные типы и не расширяй использование `any`,
    `@ts-ignore` и non-null assertions без неизбежной причины.
-   Используй функциональные React-компоненты и именованные экспорты. Следуй названию и форме
    существующего соседнего модуля; не вводи новый naming convention локально.
-   Для импортов между слоями используй абсолютные пути от `src` (`components/...`, `api/...`,
    `router/...`). Относительные импорты оставляй для файлов внутри одного локального модуля.
-   Barrel-файлы должны экспортировать публичный API каталога, а не внутренние детали. Избегай
    циклических зависимостей.
-   Соблюдай `.prettierrc` и `.editorconfig`: 4 пробела, ширина строки 100, одинарные кавычки,
    точки с запятой и trailing commas.
-   Порядок импортов и экспортов задаёт `simple-import-sort` из `.eslintrc`. Не сортируй импорты
    вручную вопреки конфигурации.
-   Не оставляй новые `console.log`, закомментированный код и неиспользуемые экспорты.
-   Не изменяй несвязанный legacy-код только ради выравнивания стиля.

## Переменные окружения

-   Конфигурация приложения загружается во время выполнения из `/env/env` до рендера React и
    доступна через `window.FEATURE_FLAGS`. Не заменяй её build-time переменными `process.env`;
    исключение — существующий `NODE_ENV` в сборочной инфраструктуре.
-   Для локальной работы скопируй шаблон:

    ```bash
    cp public/env/env.example public/env/env
    ```

-   `public/env/env` игнорируется Git. Никогда не коммить реальные внутренние адреса, access tokens,
    пароли, сертификаты и другие секреты. Не заменяй безопасные example-значения реальными.
-   Формат файла: одна пара `KEY='value'` на строку. Булевы значения записываются как `'true'` или
    `'false'`.
-   При добавлении runtime-флага синхронно обнови:
    1. `public/env/env.example`;
    2. тип `FeatureFlags` в `src/types/global.d.ts`;
    3. `nginx/scripts/99-replace-www-env.sh`;
    4. таблицу переменных в `README.md`.
-   `FLAG_EAUTH_PROXY_TARGET` — исключение: его читает только webpack dev server из локального
    `public/env/env`. Не добавляй его в `window.FEATURE_FLAGS`, `FeatureFlags` или nginx runtime env.
-   Если флаг влияет на URL API, сохраняй различие: в development запрос может идти на
    `FLAG_API_URL`, в production используются относительные nginx proxy paths из `src/api/const.ts`.

## Проверки и ограничения среды

Проект зависит от корпоративного backend и VPN. Поэтому:

-   **Не запускай browser E2E-тесты, Playwright, Selenium или ручную браузерную приёмку.** Не
    открывай браузер для проверки задачи: без VPN результат не является надёжным.
-   Не добавляй E2E-тест как подтверждение изменения. Предпочитай unit/integration тест без сети,
    статические проверки и production build.
-   Используй проверки, релевантные изменённым файлам:

    ```bash
    npm run lint:tsc
    npx eslint src --ext .ts,.tsx
    npm run lint:prettier
    npm run build
    ```

-   Для логики project assessment при необходимости доступен небраузерный тест:
    `node tests/project-assessment.cjs`.
-   `npm run lint` вызывает `lint:eslint`, а тот запускает ESLint с `--fix` и изменяет файлы.
    Не используй эту команду как read-only проверку и не допускай несвязанных автоисправлений.
-   Если полная проверка невозможна из-за отсутствия сети, backend или VPN, выполни доступные
    статические проверки и явно сообщи, что именно не было проверено.
