# Миграция с `@beeline/design-system-react` на `components/ui`

> **Статус: выполнено** (2026-06-09)
>
> Миграция завершена. Все компоненты перенесены в `src/components/ui`. Страница `/ui-dashboard` и зависимость `@beeline/design-system-react` удалены из проекта.

## Цель

Постепенно отказаться от импортов из `@beeline/design-system-react` и перенести все используемые UI-компоненты в собственную библиотеку `src/components/ui` с сохранением визуального соответствия текущей дизайн-системе и подхода к стилизации через Emotion.

## Обязательная структура каждого компонента

Для каждого нового компонента в `src/components/ui/<ComponentName>/`:

- `types.ts` — типы и пропсы компонента
- `index.tsx` — реализация компонента (только разметка и композиция, без вспомогательной логики)
- `units.ts` — стилизация через Emotion

### Опциональные файлы

Добавляются по необходимости, когда логика или данные не помещаются в обязательные файлы без перегрузки:

- `utils.ts` — вспомогательные функции компонента (нормализация пропсов, маппинг значений, проверки типов и т.п.)
- `const.ts` — константы компонента (алиасы, дефолтные значения, lookup-таблицы, размеры и т.п.)

Правила разделения:

1. `index.tsx` импортирует из `types.ts`, `units.ts`, а при наличии — из `utils.ts` и `const.ts`.
2. В `utils.ts` не хранятся стили и styled-компоненты — только чистая логика.
3. В `const.ts` не хранятся функции — только неизменяемые значения.
4. Если вспомогательная логика используется только внутри `units.ts` (например, генерация CSS по пропсам), её можно оставить в `units.ts`.
5. Если константа нужна только для стилей и не используется в `index.tsx`/`utils.ts`, её можно оставить в `units.ts`.

## Обязательный флоу работы по задаче

Каждая итерация миграции выполняется строго в этом порядке:

1. Создание компонента, дублирующего логику в `components/ui`
2. Удаление импортов из `@beeline/design-system-react` и добавление нового, кастомного компонента
3. Добавление компонента в чеклист
4. Добавление компонента на страницу `/ui-dashboard` (см. раздел «UI Dashboard»)

## Стандарты реализации компонента

1. Компонент визуально повторяет текущий аналог из дизайн-системы.
2. Пропсы совместимы с текущим использованием в проекте (обратная совместимость по месту вызова).
3. Компонент не импортирует ничего из `@beeline/design-system-react`.
4. Стили реализуются только через Emotion (`@emotion/styled`/`@emotion/react`) в `units.ts`.
5. Компонент использует существующие CSS-переменные и токены проекта.
6. Экспорт добавляется в общий реэкспорт `src/components/ui/index.ts` (или эквивалентный файл-баррель).

## Definition of Done для одного компонента

Компонент считается перенесенным, если выполнено все:

- создан `src/components/ui/<ComponentName>/types.ts`
- создан `src/components/ui/<ComponentName>/index.tsx`
- создан `src/components/ui/<ComponentName>/units.ts`
- при наличии вспомогательной логики — создан `utils.ts`
- при наличии констант — создан `const.ts`
- в проекте нет рабочих импортов этого компонента из `@beeline/design-system-react`
- использующие места переведены на `components/ui`
- компонент отмечен в чеклисте как завершенный
- компонент добавлен на страницу `/ui-dashboard` со всеми вариантами отображения

## UI Dashboard

Страница `/ui-dashboard` — визуальная витрина миграции. Расположена в `src/pages/misc/UIDashboardPage/`.

Назначение:

- показать все компоненты из чеклиста в порядке `docs/ui-migration-checklist.md`;
- слева — вариант из `@beeline/design-system-react`, справа — аналог из `components/ui` (если реализован);
- для компонентов с `variant` и другими визуальными состояниями — отобразить все возможные варианты.

Правила добавления компонента на dashboard:

1. После завершения переноса компонента создать или обновить витрину в `src/pages/misc/UIDashboardPage/showcases/`.
2. Для перенесённых компонентов — витрина в `showcases/done/<ComponentName>.tsx` с парами `designSystem` / `custom` для каждого варианта.
3. Для ещё не перенесённых — витрина в `showcases/planned.tsx` только с левой колонкой (DS).
4. Зарегистрировать витрину в `showcases/registry.ts` (порядок совпадает с чеклистом).
5. При добавлении новых вариантов пропсов — дополнять витрину, а не заменять существующие примеры.

## Правила миграции импортов

1. На каждом шаге переносить один компонент или малую связанную группу (например, `Tabs` + `Tab`).
2. Сначала переносить базовые примитивы (`Button`, `Icon`, `TextField`, и т.д.), затем сложные (`Table`, `FileUploader`, `NavigationDrawer`).
3. После каждого переноса обновлять чеклист и метрики прогресса.
4. Не смешивать крупные несвязанные переносы в одной итерации.

## Отслеживание прогресса

Прогресс фиксируется в `docs/ui-migration-checklist.md`:

- статус каждого компонента (`planned`, `in-progress`, `done`, `blocked`)
- владелец и дата обновления
- заметки по ограничениям/блокерам
- агрегированные метрики:
  - общее число импортов из `@beeline/design-system-react`
  - число завершенных компонентов
  - процент завершения

## Рекомендуемый порядок этапов

1. Подготовка каркаса `components/ui` и баррелей экспорта.
2. Перенос базовых компонентов ввода и кнопок.
3. Перенос навигационных и display-компонентов.
4. Перенос сложных составных компонентов.
5. Удаление зависимости `@beeline/design-system-react` из `package.json` после полного завершения.

## Критерий завершения всей задачи

Задача завершена, когда:

- в кодовой базе отсутствуют импорты из `@beeline/design-system-react` и `@beeline/design-system-react/types/...`
- все требуемые компоненты присутствуют в `src/components/ui`
- чеклист целиком закрыт
- зависимость `@beeline/design-system-react` удалена из проекта
